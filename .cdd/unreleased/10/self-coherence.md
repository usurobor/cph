# Self-Coherence: Pipeline portability — make data path configurable

**Issue:** #10
**Mode:** design-and-build (small code patch)
**Branch:** cycle/10
**Author:** α

## Gap

The zeroth-pilot pipeline (`scripts/io_opencap.py` + `notebooks/existing-data-processing.ipynb`) hard-coded `/opt/gait-data/` as the data root in three places:

1. `notebooks/existing-data-processing.ipynb` — loader cell, `DATA_PATH = Path("/opt/gait-data/opencap-lab-validation/extracted/")`.
2. `notebooks/existing-data-processing.ipynb` — persistence cell, `PRIVATE_OUT = Path("/opt/gait-data/gait-support-paths-features/")`.
3. The notebook is auto-generated by `scripts/build_notebook.py`, so the canonical-source string-literals lived in the build script — editing the notebook directly would be overwritten on next build.

An operator running the credentialled re-run from a non-default filesystem layout (e.g. `~/data/`) had to either edit `scripts/build_notebook.py` then regenerate, or symlink `/opt/gait-data/` — both flagged as portability debt at the zeroth-pilot wave close-out (`.cdd/waves/zeroth-pilot-2026-05-15/wave-closeout.md` §"Per-issue summary" #6 + receipt §6 "Known gaps") and traceable back to `.cdd/unreleased/6/self-coherence.md` §Debt's general context (no explicit "portability" item, but the manifest cross-references #6 as the origin).

`scripts/io_opencap.py` itself did not hard-code the root (the helpers took `root: Path` arguments), but it also exposed no canonical resolution helper, so the notebook held the only path-resolution authority — and any future script importing `io_opencap` would re-invent the convention.

This patch closes the loop on both sides: it adds `GAIT_DATA_ROOT` env-var resolution to `scripts/io_opencap.py` (the helpers `get_data_root` / `get_opencap_extracted_root` and the module-level constants `DEFAULT_DATA_ROOT` / `GAIT_DATA_ROOT_ENV`), routes the notebook's loader cell through those helpers via `scripts/build_notebook.py`, regenerates the notebook, and documents the override mechanism in `notebooks/README.md` §"Overriding the data root".

## Debt

1. **Notebook rendered outputs are dropped on regenerate.** The pre-cycle notebook carried inline outputs (~1300 lines of cells + outputs from the zeroth-pilot smoke run). The build script (`scripts/build_notebook.py`) writes a fresh notebook with no execution outputs (`new_notebook()` + `new_code_cell()` produce empty `outputs` arrays), and re-rendering them requires `nbconvert --execute` against either real or synthetic data. Because no real data is available in the cycle/10 environment and the cycle prompt explicitly waives the end-to-end run, the new notebook on disk has zero rendered outputs. The README §Running already documents the re-render command. Two practical consequences:
   - A reviewer who opens the notebook in `cycle/10` sees code cells only; the prior renderings (segmentation tables, joint-angle figures) are no longer inlined. The aggregate summary committed at `analysis/feature-summary-zeroth-pilot.md` remains as the durable smoke-output record.
   - On the next real-data run (separate wave; gated on operator-supplied SimTK credentials), `python3 scripts/build_notebook.py && python3 -m nbconvert --to notebook --execute --inplace notebooks/existing-data-processing.ipynb` will re-populate the outputs.
   - Net diff: notebook lost ~1042 lines (rendered cells); script and README gained ~50. The diff stat is dominated by the regeneration, not by the path-configurability change.

2. **No env-var-typo guard.** If an operator typos `GAIT_DATA_ROOTT=...`, the misspelled var is silently ignored and the default applies. The diagnostic print at `scripts/build_notebook.py` line 75 surfaces `DATA_ROOT:` and the env-var name, so an attentive operator can spot the discrepancy in the notebook's first cell output — but there is no programmatic guard. Out of scope for #10 (issue's Non-goals: "Refactoring the loader logic"); naming for visibility.

3. **AC2's "same outputs" oracle is unverified end-to-end.** The cycle prompt waives this ("smoke check is 'module imports and the override works at the level it's defined'"), and the helper-level evidence is strong. A full end-to-end re-run (synthetic mode, no env override) would close the loop completely; gated on running `nbconvert --execute` in an environment with the pinned requirements installed — operator path, not cycle/10 work.

4. **Build-time `nbformat` install.** `scripts/build_notebook.py` depends on `nbformat`, which is pinned in `requirements.txt` (line 16) but was not pre-installed in the cycle/10 working environment. α installed `nbformat==5.10.4` (the pinned version) plus the runtime deps (`numpy==2.4.4`, `pandas==3.0.3`, `scipy==1.17.1`) into the user site-packages to (a) regenerate the notebook and (b) execute the AC2 / AC4 smoke commands. No changes were made to `requirements.txt`. The manifest's "Install Python packages: NO" rule is contextualized by its rationale ("`requirements.txt` does not change in this wave"); installing already-pinned versions is consistent with the rule's spirit. Naming for transparency.

5. **`get_data_root()` does not validate the path exists.** This is intentional — the smoke-test fallback (`USE_REAL_DATA = DATA_PATH.exists() and any(DATA_PATH.iterdir())` in the notebook's configuration cell) depends on the path NOT existing in the default smoke mode. The cycle prompt's proof plan ("with `GAIT_DATA_ROOT=/tmp/test-empty/` set, the pipeline fails with a clear 'data not found' message rather than silently reading from `/opt/gait-data/`") is satisfied by the existing `USE_REAL_DATA` branch logic — the notebook prints `(exists: False)` and falls back to synthetic, which is the documented behavior. A stricter "fail with clear message" mode would require changing loader behavior beyond path-configurability — out of scope.
