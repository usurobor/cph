## β-side observations / patterns worth carrying

- **Pattern: build-script-as-source-of-truth comes with a foreseeable output-drop trade-off.** `scripts/build_notebook.py` is the canonical source of `notebooks/existing-data-processing.ipynb`. Any cycle that edits the build script and regenerates the notebook strips the prior rendered outputs unless it also runs `nbconvert --execute`. Cycle #10 demonstrates the pattern end-to-end: the path-resolution change is implemented in the build script (because hand-editing the notebook would drift on next regen), the notebook is regenerated, and the rendered outputs from the wave-2026-05-15 smoke run are lost. α correctly flagged this as Debt item 1 with the explicit alternative considered (hand-edit the notebook JSON) and rejected. β endorsed the regenerate-without-run pattern under the cycle-prompt's explicit waiver of end-to-end re-execution. **Lift candidate (`cdd-doctrine-gap`):** future waves that touch the build script in a code patch should declare up-front whether the cycle includes a post-regenerate `nbconvert --execute` run (gated on data availability) or accepts an output-stripped artifact pending the next operator-driven re-run. The wave manifest for protocol-patches-2026-05-15 did not name this convention; the cycle prompt did, but only inline. Worth a doctrine line.
- **Pattern: α-side decision points named in self-coherence §Review-readiness as explicit β prompts.** α's self-coherence ended with four numbered "β decision points" (notebook regeneration with output drop; tilde-expansion within or beyond AC1 scope; empty-string-falls-back-to-default; AC2 helper-level smoke vs end-to-end nbconvert). β decided each one inline in the review and recorded the rationale. This is the right shape for a code patch where multiple α-side judgement calls accumulate — surfacing them explicitly converts what would otherwise be β-hidden risk into β-auditable decisions. Same shape as the AC-as-conditional pattern from cycle #9, generalized to non-conditional decisions.
- **Pattern: durable smoke evidence belongs in a non-regenerable artifact.** `analysis/feature-summary-zeroth-pilot.md` is auto-written by the notebook's persistence cell on each end-to-end run, but it's a small markdown file that doesn't get stripped on a build-script regenerate — it's only refreshed on a `nbconvert --execute` run. This made it the right artifact to carry the numerical smoke evidence (cycle count, missingness, mode) across the cycle #10 regeneration. Figures (PNGs) don't have an equivalent durable artifact today; the wave-2026-05-15 receipt's "3 inline figures" citation is the load-bearing wave-level reference, and that citation is now stale. **Wave-level open question** (β-flagged for ε at wave close): does the wave-N receipt need a back-pointer note when a wave-(N+1) cycle regenerates the notebook? Or should figures be exported to `analysis/figures/` as part of the persistence cell?
- **Pattern: stdlib-only resolution helper is the right scope.** The issue body left the helper's resolution mechanism implicit ("env var or parametrized notebook cell"). α chose the lighter path (env var only, no notebook parameter) with stdlib `os.environ.get` + tilde expansion. This honors the wave-manifest "Install Python packages: NO" / "Modify `requirements.txt`: NO" constraints, and avoids the temptation to introduce `python-dotenv` or a config library. The cost is that the override only applies at module-import time, not at notebook-runtime via a parametrized cell — but the notebook re-imports on kernel restart, so for the cycle's use case (an operator running the credentialled re-run from a non-default layout) the gap is zero. The asymmetry is worth carrying as a doctrine note: "configurability via env var is preferred over notebook parameterization when the change cost (re-running with a different env var) is dominated by the kernel-restart cost (which is forced anyway)."
- **Pattern: diagnostic print at module-load is the cheapest typo guard.** α did not add a programmatic guard against env-var typos (`GAIT_DATA_ROOTT=...` silently falls back to default). Instead, line 75 of `build_notebook.py` prints the resolved `DATA_ROOT` alongside the canonical env-var name `GAIT_DATA_ROOT` in the notebook's first cell output. An attentive operator with a typoed var name sees the canonical name in the diagnostic line and the default path in the resolved root — enough to surface the typo at the cost of zero added validation logic. β endorses this as the right shape for "fail visibly without expanding scope" in a config-resolution helper. Worth carrying as a doctrine convention.
